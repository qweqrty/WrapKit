# Архитектурный контракт: логика отдельно, UI заменяемый

Обязателен при изменении логики, сборки экранов, навигации и UIKit/SwiftUI-переносах. Это границы ответственности, а не требование заменить архитектуру каждого приложения на одну новую. В проекте с ViewModel применяй те же границы к ViewModel; не создавай Presenter только ради названия.

## Главный инвариант

Смена UIKit на SwiftUI или другой renderer не должна требовать переписывать бизнес-сценарий. Presenter/бизнес-ViewModel принимает события и данные через контракты, возвращает presentation-модели/Output и намерения навигации. Он не знает, нарисованы ли они UIView, SwiftUI View или другой реализацией.

Отсутствия `import UIKit` недостаточно: учитывай типы, re-export, typealias и доступ к нативным API через обёртки. Не переноси UI-зависимость в Domain только потому, что её удалось скрыть другим именем.

## Сборка экрана и работа экрана — разные цепочки

```text
Сборка:
Composition root / DI
  → конкретный Flow
      → Factory.make…
          → Presenter + ContentView/View + controller/host + adapters
          → связывает Input / Output / lifecycle и возвращает готовый экран
      → Flow показывает экран в нужном стеке/контексте

Работа:
UI-событие/lifecycle → Input → Presenter → Service / Storage
                                  ↓
                           Output + PresentableModel
                                  ↓
                      ContentView или adapter → View

Presenter → Flow-контракт → конкретный Flow → Factory / навигация
```

Стрелки показывают вызовы, а не разрешение всем слоям хранить друг друга или зависеть от их concrete типов. Flow не вызывает Factory на каждый display. Factory не участвует в цикле обновления данных после создания экрана.

## Строгое распределение ответственности

| Узел | Отвечает за | Не должен делать |
| --- | --- | --- |
| Composition root / DI | Выбор реализаций; создание общих services/storages/factories/flows; межмодульные связи; lifetime долгоживущих зависимостей | Выполнять пользовательский сценарий, решать видимость кнопок, делать layout или display |
| Flow-контракт | Навигационные намерения и их смысловые параметры: открыть детали, завершить, вернуться, передать результат | Принимать UIKit/SwiftUI View, controller, Binding или navigation stack в Domain API |
| Конкретный Flow | Правильный стек/модальный контекст; вызов Factory; push/present/pop/dismiss; child flows и внешние callbacks | Загружать данные экрана, валидировать ввод, форматировать текст, собирать presentation-модели, настраивать поля/шапку |
| Factory | Создать Presenter, UI, host и adapters; внедрить зависимости; связать Input/Output/lifecycle; вернуть готовый экран | Выполнять запросы/сценарий, подписываться на продуктовые данные вместо Presenter, вызывать display/lifecycle вручную, менять constraints/layout |
| Presenter / бизнес-ViewModel | Состояние сценария; обработка Input; валидация; вызовы service/storage/use case; преобразование данных в presentation-модели; loading/error/empty; продуктовая аналитика; намерения Flow | Знать concrete View/controller/host; выполнять push/present; управлять constraints/frame или нативными API keyboard/focus/UIKit; решать, какой renderer используется |
| Input / Output / PresentableModel | События, команды отображения, данные и смысловые настройки между логикой и renderer | Передавать concrete View/controller, замыкать весь service container или требовать нативный lifecycle-объект |
| ContentView / SwiftUI View | Создание визуальной иерархии; layout; отображение готовой модели; адаптация к доступному размеру/теме; технические focus/scroll/keyboard; передача действий в Input | Выполнять сеть, читать продуктовые storage, интерпретировать DTO/error-коды, проверять бизнес-правила, выбирать продуктовый маршрут или обращаться к Flow напрямую |
| Controller / host / SwiftUI adapter | Нативная граница; forwarding lifecycle/events; применение Output к UI; хранение observable presentation-state; технические delegates/data sources | Становиться вторым Presenter: загружать данные, повторять валидацию/форматирование, выбирать продуктовые переходы |
| Service / Repository / Storage | Получение, преобразование и хранение данных; API/DTO/ошибки на границе данных; согласованный контракт отмены/завершения | Знать экран, шапку, alert, цвет кнопки или navigation controller; напрямую обновлять UI |

Бизнес-правило, общее для нескольких сценариев, может жить в уже принятом domain service/use case. Presenter вызывает его, а не копирует правило в каждый экран. Не создавай новый use-case слой для каждой функции без необходимости.

## Допустимые зависимости и native-граница

- Domain/бизнес-логика/Presenter не импортируют UIKit, SwiftUI, AppKit и не зависят от iOS/UI-target. Они используют данные, абстракции и только явно объявленные зависимости.
- Платформенные возможности — camera/contacts/permissions/device и подобные — передаются в логику через существующие протоколы и нейтральные результаты. Их SDK/реализация остаются снаружи Domain.
- Presenter получает конкретно необходимые service/storage/flow/output-контракты через DI. Не получает глобальный resolver, весь UI container или другую Factory как способ достать её внутренние services.
- View принимает Input и presentation-state/модель. Presenter знает Output-контракт, а не concrete View. Native-данные событий преобразуются на UI-границе в смысловой Input.
- Domain Flow/Factory-протоколы не требуют UIKit-типы. Generic `Factory<Controller>` с `associatedtype Controller` допустима: конкретная iOS Factory связывает его с UIViewController снаружи Domain. Не добавляй универсальную обёртку поверх уже подходящего контракта.
- Конкретные iOS Flow/Factory/controller/host вправе использовать UIKit/SwiftUI для создания, композиции и навигации. Это не нарушение само по себе. Нельзя запретить UIKit в платформенной Factory, а затем вернуть push/present в Presenter.
- Native conversion, resource bundle lookup, UIImage/UIFont/Color bridges, frame/constraints и trait/geometry adaptation принадлежат UI/компоненту/adapter в соответствии с его слоем. В Domain передавай смысл/данные через принятый контракт, не нативный control.
- В текущих shared presentation-контрактах бывают платформенные aliases, например Image/Color/Font. Это существующее ограничение, не доказательство полной платформонезависимости. Использование принятых Output-моделей/токенов не разрешает добавлять в Presenter новые native API или скрывать зависимость ещё одним alias. Если для задачи контракт протаскивает новый native тип, вынеси преобразование на UI-границу либо обозначь и согласуй изменение контракта; не переписывай молча весь framework.

## Presenter определяет «что», View — «как»

- Presenter определяет текст, доступные продуктовые действия, enabled/disabled по правилам сценария, состояние loading/empty/error и смысловое оформление через имеющиеся Output-модели/токены.
- ContentView определяет размещение, перенос строк, скролл, safe area, focus, доступность поля при клавиатуре и техническое отображение этих настроек. Нативное применение стиля и адаптация к UIKit/SwiftUI происходят здесь либо в общем компоненте.
- Нейтральное намерение Presenter через существующий Output, например `startEditing()`/`stopEditing()`, допустимо. View исполняет его нативными средствами и обеспечивает видимость поля; Presenter не вызывает firstResponder/keyboard API и не считает keyboard frames.
- UI-ветвление по готовому состоянию допустимо: показать loading, выбрать HStack/VStack по размеру, отобразить `model.isEnabled`. Бизнес-ветвление по тарифу, балансу, статусу абонента или ответу сервера должно сформировать это состояние до View.
- В NUR.Features настройка `HeaderOutput.display(model/style/…)` принадлежит Presenter. Factory только связывает header output; ContentView/adapter применяет переданный стиль. Не дублируй продуктовую настройку шапки в Factory, `ContentView.didSet` или SwiftUI `.onAppear`.
- Конструктор UI-компонента вправе задать его нейтральное/согласованное default-оформление. Это не повод задавать продуктовый текст, CTA, back action или состояние экрана из Factory.
- `display(model: nil)` скрывает блок. Shimmer управляется отдельно. Повторные display соблюдают контракт: полная модель обновляет её состояние, частичный `display(text:/isEnabled:/onPress:…)` меняет указанные свойства, не сбрасывая остальные без основания. При замене/удалении действия не должен оставаться старый callback или пустая активная кнопка.

## Lifecycle, события и владение

- UI пересылает lifecycle в Input/принятый lifecycle-контракт. Factory связывает его, но не вызывает `viewDidLoad()`/`onAppear()` вручную для показа первого состояния.
- SwiftUI `.task`/`.onAppear` могут переслать событие в Input; не должны сами запускать service/storage или повторять бизнес-логику. Сохрани семантику первого/повторного появления; не создавай Presenter, subscriptions и service graph заново из `body`.
- Кнопка передаёт событие в Input либо выполняет action из готовой Output-модели. Решение «можно ли продолжить» и выбор следующего продуктового шага — в Presenter/domain-логике; Flow выполняет намерение в нужном контексте.
- При сборке установи владельца Presenter/Input и adapters на всё время жизни экрана. Не допускай преждевременного deinit, цикла Presenter → output → View → Presenter или потери child flow до результата.
- Выбирай weak/strong по графу владения; не ставь weak везде автоматически. Для escaping callbacks, способных удержать владельца, избегай retain cycle. Доставку UI обновлений и cancellation сохраняй через принятые decorators/контракты.
- При закрытии/смене сессии поздний результат не должен оживлять старый экран/сценарий. Сохраняй принятый контракт отмены и однократного завершения, не лечи это скрытой подпиской в View/Factory.

## Что при ревью считать нарушением границы

- В Factory появились `display`, запрос/продуктовая subscription, ручной lifecycle, тексты/CTA или constraints.
- В Presenter появились UI imports/concrete controls, UIViewController/Binding, нативная навигация, layout или ветка «если SwiftUI/если UIKit» для бизнес-правила.
- В ContentView/adapter появились services/storages/Flow, расшифровка DTO/error-кода, форматирование по продуктовым правилам или дубликат валидации Presenter.
- Flow стал готовить содержимое экрана или выполнять запрос, от результата которого Presenter должен построить свой UI.
- Сервис стал показывать alert/loader или напрямую менять экран.
- Для UIKit и SwiftUI продублированы Presenter/сценарий/запросы вместо замены renderer и UI-связки.
- Новая обёртка/alias лишь прячет запрещённую зависимость; либо Factory проксирует внутренности другой Factory вместо нормального DI.

Существующее нарушение не становится образцом. Не устраивай массовый рефакторинг вне задачи: новое нарушение не добавляй, пересекающееся с задачей исправь в согласованном объёме, остальное явно обозначь.

## Проверка перед завершением

Для затронутого кода ответь: кто создал зависимости, кто запустил сценарий/запрос, кто подготовил модель, кто отрисовал её и кто выполнил переход? Для каждого действия должен быть один понятный владелец.

Проверь imports и фактические типы в изменённых контрактах, связи Input/Output/lifecycle, lifetime/cancellation, отсутствие бизнес-дубликатов между renderers. Подтверди поведение релевантными проверками по профилю проекта и просмотром снимков для UI. Не требуется новый хрупкий unit-тест на каждый внутренний шаг Presenter.
