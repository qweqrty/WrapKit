# Проверка iOS UI-сценариев

Зелёный тест подтверждает выполнение, а не правильный экран и не визуальный паритет.

```text
Приложение: требование → имя теста → Scenario → ответы/данные → действия → assertions → снимок шага → проверка содержимого
Компонент: контракт → имя snapshot-теста → setup/model → display/action/layout → assertions → снимок состояния → проверка содержимого
```

Следуй правилам репозитория. Этот workflow не даёт разрешения исправлять код во время read-only ревью, менять эталоны или публиковать результаты.

Skill общий для библиотек и всех приложений команды, не только Features. Выбирай профиль проверок из `.agents/project-context.md`: unit и snapshots в WrapKit; пользовательские сценарии в Features/приложениях; без отдельной обязательной большой матрицы в DesignSystem. Зелёные unit-тесты не заменяют снимки UI.

Если запрос ограничен предоставленными картинками и репозиторий/прогон не входят в задачу, проверь доступные кадры и их происхождение. Не требуй полный запуск для ответа на узкий визуальный вопрос; явно отдели наблюдение на картинке от подтверждённой причины в коде. Шаги про git, fixtures и сборку ниже применяй, когда исходники доступны и такая проверка входит в задачу.

Полнота относится к согласованному виду проверки: наблюдение по предоставленному кадру не является полным регрессом, а проверку всех затронутых сценариев нельзя сужать до удобной выборки без изменения задачи пользователем.

## 1. Зафиксируй объём и происхождение

- Проверь ветку, git status и diff. Определи head и согласованный baseline; проверь реальные revisions собираемых зависимостей.
- Для UI-сценария найди имя теста, Scenario/raw value, упорядоченные ответы/JSON, действия и точки снимков. Для повторяющегося роута проверь последовательность ответов. Для snapshot найди модель/setup, настройки компонента и последовательность display/action/layout; не требуй выдуманный backend/Scenario.
- Определи ожидаемый результат: экран, заголовок, содержимое, loading/empty/error, кнопки, sheet и итог навигации. Не считай ожидаемым то, чего нет в требованиях или подтверждённом baseline.
- Определи полный затронутый объём по diff, изменённым контрактам и прямым/косвенным потребителям, включая экраны в зависимых проектах. Найди относящиеся к нему сценарии, состояния, переходы и обязательные кадры; не подменяй этот объём удобной выборкой или фиксированным списком экранов. Для переноса сравни UIKit и SwiftUI.
- Веди учёт покрытия: что требуется проверить, какие полные test identifiers запущены и с каким результатом, какие кадры каких шагов действительно просмотрены или подтверждены автоматикой по контракту ниже. Для большого объёма сохрани компактный реестр вне git; для малого достаточно точной связи в ответе. Найденный, но не запущенный сценарий и только сохранённый PNG остаются пропусками.
- До прогона сохрани существующие артефакты, которые будут перезаписаны. Не создавай clone/worktree или большую копию build cache ради сравнения без согласования.

## 2. Выполни релевантную проверку

- Прочитай актуальные manifests, Makefile, схемы и CI. Выбери существующую схему и доступный simulator; не угадывай команду и не запускай publish/release-операции.
- Сначала запусти узкие изменённые сценарии; после их исправности — весь оставшийся затронутый объём. Порядок запуска не сокращает требуемое покрытие. Не строй полное приложение ради правки инструкции.
- Разделяй ошибки подготовки/сборки, падение теста и дефект продукта. Если сборка блокирует запуск, сообщи первую содержательную ошибку и границу выполненной проверки.
- Не используй simulator, занятый другим прогоном. Убедись, что открылись нужное приложение и нужный Scenario. Не сбрасывай чужой simulator для решения конфликта.
- Подтверждай итоговый пользовательский результат assertions, а не только tap, ожиданием idle или снятием скриншота. Не меняй тесты в read-only ревью без запроса на исправление.

## 3. Проверь снимки и последовательности

- Само получение PNG не завершает этот шаг. Каждому заявленному кадру сопоставь test identifier, сценарий/setup, шаг и ожидаемое содержимое. Имя файла — указатель, не доказательство.
- Проверь содержимое просмотром оригинала агентом/разработчиком либо автоматической проверкой явно заданных признаков: экран/компонент, конкретные данные/тексты, состояние, видимость нужных/запрещённых действий и layout. OCR строки без проверки контекста и pixel diff сами по себе не являются семантической проверкой.
- Автоматическое подтверждение должно указывать проверенные признаки и ограничения. Для принятого baseline можно использовать совпадение кадра при неизменных контракте/данных/окружении; неизвестный или уже ошибочный baseline не становится правильным от совпадения. Новые/изменённые/сомнительные кадры и признаки вне автоматики требуют просмотра.
- В результате раздели: «содержимое проверено», «есть дефект», «только захвачено, не проверено». Если название теста обещает иной результат, проверь реализацию и fixtures: не переименовывай кадр только для маскировки расхождения. Необязателен отдельный файл-реестр; достаточно компактной связи в ответе для проверяемого объёма.
- Сопоставляй снимки по сценарию и шагу, а не только по имени PNG. Сверяй ОС, устройство/размер окна, ориентацию, локаль, тему, размер текста, accessibility-настройки, режим fullscreen и keyboard state.
- Снимки с несовместимым окружением можно изучать отдельно, но нельзя использовать как доказательство паритета. Candidate-only сценарий показывает новую реализацию, а не отсутствие регрессии.
- Для каждой последовательности проверь переходы между кадрами: запрос → ответ → действие → новое состояние. В output-компонентах проверь повторные display, скрытие/возврат модели, смену данных, loading и повторное использование там, где это затронуто.
- Authorization вместо нужной фичи, неожиданный вечный shimmer, старые fixtures или экран другого приложения — недостоверное подтверждение, даже при passed.
- При наличии сопоставимого baseline сначала отфильтруй снимки по hash, размерам и pixel diff. Изучи изменённые, пропавшие и семантически подозрительные кадры в полном разрешении; неизменившийся hash не доказывает правильность сценария. Без пары до/после изучи доступные кадры отдельно и не заявляй паритет.
- Включай все затронутые состояния и переходы; оценивай риск, чтобы выявить их, а не исключить из проверки. Учитывай темы, длинные/многострочные строки, dynamic colors, шапки и кнопки, loading/empty/error, keyboard/scroll, возврат и повторное открытие там, где они связаны с изменением. Не объявляй полное покрытие по нескольким кадрам.
- Для изменений навигации/адаптивной вёрстки учитывай доступные старые и новые ОС, rotation, размеры окна, Duo/Split View и оба значения UIRequiresFullScreen, когда они относятся к задаче. Недоступные окружения перечисли отдельно; не эмулируй их под видом реального прогона.
- Важный визуальный дефект проверь на исходном PNG в полном разрешении и, при необходимости, по пикселям/frames/constraints или повторному воспроизведению. Увеличенный preview и JPEG-галерея не заменяют оригинал.

## 4. Инструменты сравнения

Markdown-ссылки на references разрешай от папки этого skill, независимо от способа вызова. Примеры shell-команд ниже выполняются **из корня репозитория**; в другой рабочей папке используй абсолютный путь к helper.

Для сравнения есть `scripts/visual_compare.py` (Python 3, Pillow, NumPy). Используй уже доступный runtime. Если зависимостей нет, сообщи об этом; установку и внешние загрузки выполняй в рамках разрешений окружения, не меняя глобальный Python.

```sh
python3 .agents/skills/ios-ui-scenario-review/scripts/visual_compare.py \
  --before /absolute/path/to/before \
  --after /absolute/path/to/after \
  --output /absolute/path/to/temporary-review
```

- Входные папки должны существовать, содержать ожидаемые кадры и не совпадать с output. Сначала проверь их: пустой отчёт не является успехом.
- Скрипт создаёт `index.html`, `report.json` и обзорные изображения. Его exit code и pixel threshold — не вердикт о корректности UI.
- Он сопоставляет относительные имена. Переименованные кадры проверь по шагам; missing_before/missing_after не называй новой/удалённой фичей без проверки исходников.
- Обзорные сравнения сохраняются с JPEG-сжатием; мелкий текст, цвет и размытие подтверждай оригинальными PNG. Для полной сводки не используй `--changed-only`: она скрывает unchanged entries.
- Сохраняй исходные PNG; метрики, OCR и галерея помогают отбору, но не заменяют проверку смысла.

OCR доступен через `scripts/ocr_images.swift` на macOS с Vision/AppKit и Xcode command-line tools:

```sh
xcrun swift .agents/skills/ios-ui-scenario-review/scripts/ocr_images.swift /absolute/path/to/image.png
```

Текущий helper запрашивает ru/ky/en. Проверяй поддержку языков текущим runtime; для других локалей и при ошибке OCR читай исходный кадр, не делай вывод «текста нет». OCR необязателен.

## 5. Достоверность результата

Перед выводом используй [контракт подтверждений](references/evidence-contract.md).

- Не обновляй baseline, tolerance и настройки захвата, пока не установлена причина различий. Не называй падение флейком только потому, что повторный запуск прошёл.
- Компонентный snapshot/probe доказывает состояние компонента. Он не подтверждает интеграцию фичи, маршрутизацию, реальную работу бэка или полный экран приложения.
- Не подставляй рассчитанные значения в нарисованный вручную «скриншот продукта». Диагностическую обвязку, синтетические данные и отличия от полного dependency graph явно обозначай.
- После последней правки или разрешения конфликтов пересмотри затронутый объём и повтори проверки, результат которых она могла изменить. Снимки от другой версии компонента/зависимости не подтверждают текущую реализацию; сохрани фактические revisions проверенной сборки.
- Проверка завершена только когда весь требуемый затронутый объём выполнен и содержимое всех обязательных кадров проверено. Найденный и подтверждённый дефект — результат проверки, а не пропуск; завершённость проверки отделяй от готовности исправления или разрешения на merge. Любой пропущенный, skipped или заблокированный сценарий из требуемого объёма, отсутствующий или непроверенный обязательный кадр означает «проверка не завершена»; укажи конкретный пробел. Нельзя объявлять готовность по числу passed или просмотренных снимков без сопоставления с требуемым покрытием.
- Если требуется паритет с baseline, его отсутствие или несовместимость оставляет эту проверку незавершённой. Candidate-only кадры могут подтверждать наблюдаемое состояние, но не закрывают требуемое сравнение.

## Результат для пользователя

Кратко укажи:

Для визуального вывода покажи связь «test → шаг/setup → ожидаемое → что видно» и статус проверки содержимого, а не только список сохранённых PNG.

1. Подтверждённые проблемы/изменения с реальными до/после или последовательными изображениями. В локальном чате используй абсолютные пути; в MR — доступные артефакты, а не путь с чужого компьютера.
2. Где именно дефект: файл и линия при доступных исходниках; иначе путь к кадру и наблюдаемая область. Укажи условие, фактический и ожидаемый результат. Гипотезы о причине подпиши отдельно.
3. Как требуемый затронутый объём покрыт запусками: полные test identifiers, passed/failed/skipped, окружение, baseline/head, revisions зависимостей и источник снимков.
4. Какие кадры/шаги просмотрены, какие признаки проверены автоматически и какие сценарии/состояния/кадры пропущены. При любом пропуске явно напиши «проверка не завершена»; отсутствие baseline и необходимость проверки человеком укажи отдельно.

Не заявляй «всё проверено», «регрессий нет» или «можно мержить» по одному pipeline. При неполном покрытии допустим только промежуточный вывод: «В проверенной части необъяснённых визуальных различий не найдено; проверка всего затронутого объёма не завершена: …».
