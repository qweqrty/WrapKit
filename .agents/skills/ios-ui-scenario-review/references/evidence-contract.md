# Контракт подтверждений

Используй его для UI-реализации, ревью и проверки перед merge. Не требуй машинный отчёт для каждого маленького изменения; требуй проверяемое происхождение вывода.

## Что должно быть известно

Для проверенного сценария зафиксируй:

- требование/Jira и полный test identifier;
- Scenario/raw value, пути к fixtures и порядок ответов роутов;
- действия, assertions, порядок и смысл снимков;
- baseline/head SHA и фактические revisions изменённых зависимостей;
- device/OS, ориентацию/размер окна, локаль, тему и прочие влияющие настройки;
- результат теста и источник изображения: xcresult, CI artifact или локальный capture;
- что сравнивалось и почему видимое изменение допустимо либо ошибочно.
- результат проверки самого содержимого: какой test/шаг/setup обещает этот кадр, что ожидалось и что действительно видно; просмотрено ли оно человеком/агентом либо какие конкретные признаки проверены автоматически.

Для компонентного snapshot укажи setup/model и последовательные display вместо отсутствующих роутов. Для ручного воспроизведения укажи шаги и фактически запущенный build. Неприменимые поля не выдумывай.

Unit-тест контракта, snapshot-тест и просмотр snapshot — отдельные подтверждения. Особенно в WrapKit не пропускай последний шаг из-за зелёного unit/snapshot suite.

## Проверка самого кадра

Для каждого заявленного сценария свяжи тест и снимок по шагу. Проверь, соответствует ли фактическая картинка обещанию теста и ожидаемому состоянию: нужный экран/компонент, данные, loading/empty/error, видимость действий, цвет и layout в затронутом объёме.

Сопоставление имён или наличие файла — только проверка происхождения, не содержимого. Автоматически можно проверить конкретные признаки или совпадение с ранее принятым baseline при совместимом окружении и неизменном контракте. Укажи границы такой проверки; OCR/pixel diff без этих условий недостаточны. Новые, изменённые и сомнительные кадры нужно просмотреть.

Используй явные статусы: **содержимое проверено**, **дефект**, **захвачено, но не проверено**. Последний статус не включай в визуально подтверждённое покрытие. Если снимок не совпадает с обещанием имени теста, выясни причину в сценарии/модели/шаге; не исправляй только название ради формального совпадения.

Если снимки уже передал пользователь и происхождение неизвестно, исследуй их как предоставленные данные. Не приписывай им конкретный commit или simulator без подтверждения.

## Разделяй виды проверки

| Вид | Что подтверждает | Чего не подтверждает |
| --- | --- | --- |
| Статический анализ | Конкретный путь кода и условие дефекта | Реальное выполнение или внешний ответ бэка |
| Unit-тест/formatter probe | Поведение изолированной логики на выбранных входах | Полный UI и интеграцию |
| Component snapshot | Рендер компонента при указанном setup | Вызов из нужной фичи и полный flow |
| UI-тест + просмотр кадров | Выполненный сценарий и видимые состояния | Другие сценарии/ОС/размеры и работу production-бэка |
| До/после в совместимом окружении | Паритет в указанном объёме | Полное отсутствие регрессий во всём приложении |

Стабы — допустимые данные тестов, но не свидетельство фактического API. Диагностическая обвязка не является экраном приложения. Не улучшай, не дорисовывай и не генерируй изображения, выдаваемые за доказательство UI.

## Статус вывода

- **Подтверждено в проверенном объёме:** верный сценарий, пригодное происхождение, совместимое сравнение и объяснённые различия. Это материал для решения человека, не гарантия релиза.
- **Частично проверено:** есть полезные снимки/тесты, но отсутствует baseline, часть состояний или окружений. Перечисли пробелы.
- **Не подтверждено / проверка заблокирована:** тест не запустился, открылся другой экран, источник устарел/неизвестен либо несовместим. Отдельно укажи статически доказанные ошибки; заблокированный UI-прогон их не отменяет.

## Новые, удалённые и общие сценарии

- Новый сценарий подтверждай отсутствием его исходника в baseline; покажи конечный пользовательский результат и необходимые промежуточные шаги. Не называй candidate-only снимок доказательством паритета.
- Для пропавшего сценария установи: удалили тест, переименовали снимки, не выполнили путь или удалили продуктовый функционал. Не делай вывод только по отсутствующему PNG.
- Для общего компонента проверь изменённое поведение и представителей затронутых потребителей. Остальных обозначь непроверенными; не дублируй одинаковое отличие сотнями кадров.

## Что не является одобрением

- passed без проверки правильного экрана;
- малый pixel diff без понимания содержимого;
- пустой comparison report;
- зелёный повтор после падения без установленной причины;
- скриншот другой ОС/темы/сценария;
- вычисленный пример или нарисованный макет вместо реального capture;
- новый baseline, принятый только ради зелёного CI.
