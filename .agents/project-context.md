# Профили проектов и проверок

Выбери профиль по реальному назначению репозитория/таргета, не только по имени папки. Прочие профили не требуют внедрять их архитектуру или тестовую инфраструктуру. Schemes, deployment target, SDK, команды и существующие тесты проверяй по актуальным manifests и CI.

Независимость логики от renderer и обязанности Flow/Factory/Presenter/View заданы в [архитектурном контракте](architecture.md). Он применяется и к приложениям с ViewModel под их существующими именами; конкретная native-композиция не переносится в Domain.

## WrapKit — универсальная библиотека

- Здесь контракты и инфраструктура для любых текущих и будущих приложений: без продуктовых условий, корпоративных ресурсов и зависимостей на Features/DesignSystem.
- Сохраняй публичные API, generic constraints, платформенную доступность и default-поведение потребителей. Для локального исключения сначала рассмотри явную настройку, а не глобальную смену значения по умолчанию.
- Изменённую логику проверяй unit-тестами: результат/ошибка, nil, отмена, число завершений/подписок, порядок событий, lifetime и delivery context — в зависимости от затронутого контракта. Unit-тесты UI state model полезны, но не заменяют рендер.
- Для UI-изменений обязательны релевантные snapshot-тесты и содержательная проверка снимков. Основной объём работы может быть именно здесь: собрать правильные состояния и объяснить origin/new/diff, а не просто прогнать suite.
- Связка snapshot: имя теста → setup/model → последовательность display/action/layout → assertion → снимок → проверка содержимого. Backend-роуты для изолированного компонента не требуются.
- Покрой изменённые состояния и переходы: разные входы, повторный display, nil → model, скрыть → показать, reuse/reset, enabled/disabled, темы/динамические цвета, длинный текст — по затронутому поведению, не ради полного комбинаторного перебора.
- Новое/изменённое SwiftUI-представление проверь на паритет с UIKit там, где обещан одинаковый контракт, и добавь в существующий соответствующий каталог при наличии такого каталога.
- Проверь реальные потребители изменённого контракта в DesignSystem/Features/приложениях. Необследованные потребители остаются непроверенными; один snapshot не доказывает безопасность всех приложений.

## DesignSystem — общее для компании

- Здесь общие корпоративные UI-компоненты, фирменные стили, токены, строки и ресурсы. Универсальный нижний слой — WrapKit; правила конкретного продукта не нужно обобщать сюда.
- Сохраняй resource bundles, платформенные guards и разделение ресурсных/UI-модулей. Accessors и protocol wrappers регенерируй из исходников.
- Отдельную обязательную большую unit/UI/snapshot-матрицу для каждого изменения не вводи. Собери затронутый target; существующие релевантные тесты используй, если они есть. Не утверждай, что тестов нет, и не удаляй их из-за этого профиля.
- Изменённый UI/стиль/ресурс проверь в существующем каталоге либо реальном потребителе, если изменение влияет на отображение. Зафиксируй, какую реализацию и какой путь потребителя проверил. Генерация ресурсов не заменяет проверку их отображения.

## NUR.Features — продуктовые сценарии My O

- Сохраняй принятые Domain/Presenter/Input/Output/Flow/Factory и код-стайл. Domain/Presenter не импортируют UIKit/SwiftUI и не зависят от конкретной iOS View.
- Presenter формирует модели и вызывает Output; ContentView/SwiftUI View реализует отображение. Factory собирает зависимости и связывает контракты, но не вызывает display.
- Включая стиль шапки, `HeaderOutput.display(...)` должен вызываться из Presenter, а не Factory, ContentView.didSet или дополнительного SwiftUI side effect. Используй общий navigation/header и существующий HeaderOutput вместо самодельных title/back.
- `display(model: nil)` скрывает блок; shimmer — отдельное состояние. Сохраняй контекст субномера и исходный маршрут завершения flow.
- SwiftUI adapters, WeakRef, main-queue decorators и spies используй из Sourcery. Не заводи ручной дубликат генерируемого адаптера.
- Один UI-тест — одна user story. Проверь маршрут до результата, упорядоченные fixtures/ответы, действия, assertions и смысл каждого заявленного кадра. Для переноса из Alga сравни исходное поведение; для SwiftUI — UIKit baseline.
- Unit-тесты выбирай для значимого поведения, а не фиксации всех внутренних шагов Presenter. UI-паритет ими не подтверждается.

## Приложения и продуктовые библиотеки

К этому профилю относятся Alga, Dashboard, Registrator, PhotoStore, Automatron и другие приложения/продуктовые модули команды. Общее правило ответственности действует во всех них, даже когда они пока не используют Features.

- Держи продуктовые правила, сценарии, навигацию и интеграцию в соответствующем приложении/модуле. Универсальное выделяй в WrapKit, корпоративное UI — в DesignSystem, только в рамках согласованной задачи и реальной потребности.
- Сохраняй местную архитектуру и ограничения модулей: ViewModel/Presenter, Flow/Coordinator, DI, app extensions, разрешённые зависимости и ресурсы. Не заменяй местный стек на архитектуру Features из-за общего AGENTS.md.
- Используй существующие unit/UI/snapshot-тесты по затронутому поведению. Если UI-инфраструктуры нет, не создавай её попутно: выполни доступную сборку и согласованное ручное воспроизведение, явно укажи пробел автоматизации.
- Скриншоты реального приложения сопоставляй с пользовательским сценарием и проверяй содержимое по общему skill. Unit/probe отдельной функции не выдавай за интеграционный flow.
- Общие инструкции при внедрении дополняют действующие локальные договорённости. Не удаляй из старого AGENTS/CLAUDE правила модулей, безопасности, extensions, DI или сборки, не перенеся их в актуальный локальный guide.
